# Verified SQL Error Diagnosis and Repair with Schema-Aware Code Transformers

*Draft — all numbers are produced by `python -m evaluation.evaluate` (see `reports/evaluation_report.md`).*

## Abstract

Database error messages tell users *that* a query failed, rarely *why*, and say nothing at all about queries that
run but are logically wrong. We present SQLDiagnose, a system that assigns a SQL query to one of eight error
classes, explains the decision, and proposes a repair that is **verified** before it is returned. Its core is a
deterministic analyzer that compiles the query against an empty database with the target schema and applies
portable AST rules; it labels a dataset of 9450 queries built by injecting 25+ kinds of realistic errors into
Spider, keeping only samples whose label the analyzer confirms. A code transformer (CodeBERTa-small, 84M parameters,
trained on a laptop CPU) that reads the query together with a compact schema description reaches **87.4% accuracy /
87.6 macro-F1 on databases never seen in training**, against 51.3 for a TF-IDF baseline; without the schema
input it drops to 47.0. A generate-and-verify repair engine fixes 86.3% of erroneous test
queries (restoring the exact original in 63.4%), and wrapping a small text-to-SQL model with
verification and repair raises valid SQL from 54.0% to 88.0% and execution accuracy from
40.0% to 54.7% for a 0.5B-parameter code LLM running on CPU.

## 1. Introduction

A failing query produces messages such as `near "x": syntax error`, and a query that compares a column with
`= NULL`, forgets a join condition or selects non-grouped columns often produces no message at all. Tools for
SQL learners, query editors and text-to-SQL systems need a finer answer: which kind of error, where, and how to
fix it. Prior neural approaches treat the problem as text classification of the query alone, which cannot decide
schema-dependent errors (does column `nme` exist?) and whose labels, when generated by mutation, are only as
reliable as the mutation's intent.

We make three contributions:

1. **Verified labels.** A deterministic analyzer (SQLite compilation of the query against an empty in-memory
   database with the schema, plus AST rules for portability, type and join errors and an access-policy check)
   serves as the label oracle. Every synthetic sample is kept only if the analyzer independently assigns the
   intended class, and the analyzer is audited on 8034 human-written Spider queries.
2. **Schema-aware classification.** The classifier reads `query </s></s> schema` and is evaluated on databases
   disjoint from training; an ablation quantifies the value of the schema input.
3. **Verified repair.** Class-specific candidate generators feed a verify-and-select loop, so a reported repair
   always passes the analyzer, and multi-error queries are repaired step by step.

## 2. Error taxonomy

| Class | Decided by | Typical cause |
|---|---|---|
| CORRECT | analyzer | — |
| SYNTAX_ERROR | engine | misspelled/missing keyword, comma, parenthesis, quote, operand |
| UNKNOWN_TABLE | engine | typo, singular/plural confusion, table from another database |
| UNKNOWN_COLUMN | engine | typo, column of another table, undefined qualifier |
| DATATYPE_MISMATCH | AST rules + types | numeric column vs. text literal, text column vs. number, SUM/AVG of text |
| AMBIGUOUS_REFERENCE | engine + AST | unqualified column in several joined tables, reused alias |
| PERMISSION_DENIED | access policy | restricted table/column, including via `*` |
| SEMANTIC_ERROR | engine + AST | aggregate in WHERE, GROUP BY violations, `= NULL`, missing join condition, arity mismatches, unknown functions, self-comparisons |

PERMISSION_DENIED depends on an external policy, not on the query text, so it is decided only by the policy
check (100.0% on 400 query/policy pairs) and excluded from the learned classes.

## 3. Dataset

Correct queries are Spider gold queries that pass the analyzer (96.5% of all gold queries do; the rest are
genuine problems such as GROUP BY violations under standard SQL or joins without conditions). Mutation operators edit
exact character spans of a correct query, so only the error itself changes. Keyword case, spacing, numeric literals
and alias names are randomised for every class so they carry no label signal. The splits are database-disjoint:
7000 training queries from 119 databases, and 1400 test queries from the 20 Spider-dev
databases, balanced over the seven learned classes.

## 4. Models

* **Classifier.** `huggingface/CodeBERTa-small-v1` (6 layers) fine-tuned for 3 epochs (batch 16, lr 5e-5, linear
  schedule, max 256 tokens), then for 2 more epochs from the best checkpoint at lr 2e-5, keeping the checkpoint with
  the best validation macro-F1 (0.842 → 0.872). Total compute was about 7 hours on a 2-core laptop CPU. The schema segment lists the columns and
  coarse types of the tables the query mentions, then the names of the other tables.
* **Baseline.** Logistic regression on word (1–3) and character (2–5) n-gram TF-IDF of the same input.
* **Repair engine.** For the analyzer's primary issue: edit-distance keyword correction, fuzzy and foreign-key-aware
  identifier matching, alias qualification, foreign-key join inference, AST rewrites and a bounded single-edit
  search. Candidates are re-analyzed; the engine keeps the one that removes the issue with the highest prior and
  smallest edit, and iterates.

## 5. Results

### 5.1 Classification on unseen databases

| System | Accuracy | Macro-F1 (95% CI) | ROC-AUC | ECE |
|---|---|---|---|---|
| TF-IDF + LogReg | 53.1 | 51.3 (48.7–53.7) | 87.6 | 0.120 |
| CodeBERTa-small-v1 | 87.4 | 87.6 (86.0–89.2) | 98.5 | 0.071 |
| CodeBERTa-small-v1 (no schema input) | 47.1 | 47.0 (45.0–48.9) | 82.9 | 0.456 |

The transformer outperforms TF-IDF on 525 test queries and underperforms on 45
(McNemar p = 8e-105). Removing the schema input costs 40.6 macro-F1 points, concentrated on
schema-dependent classes, which confirms that these errors are not decidable from the query alone.

| Class | Precision | Recall | F1 |
|---|---|---|---|
| CORRECT | 61.1 | 81.0 | 69.7 |
| SYNTAX_ERROR | 98.3 | 88.5 | 93.2 |
| UNKNOWN_TABLE | 97.5 | 96.5 | 97.0 |
| UNKNOWN_COLUMN | 81.4 | 63.5 | 71.3 |
| DATATYPE_MISMATCH | 93.3 | 97.0 | 95.1 |
| AMBIGUOUS_REFERENCE | 94.8 | 92.0 | 93.4 |
| SEMANTIC_ERROR | 94.0 | 93.5 | 93.7 |

The weakest class is UNKNOWN_COLUMN (recall 63.5%): most misses are predicted CORRECT, i.e. the model does not
notice that a plausible-looking column is absent from the listed columns. Table-level errors, which require only
matching against a short list of table names, are recognised almost perfectly.

### 5.2 Repair

| Class | Verified fix | Exact recovery |
|---|---|---|
| SYNTAX_ERROR | 98.0 | 93.0 |
| UNKNOWN_TABLE | 97.5 | 95.5 |
| UNKNOWN_COLUMN | 79.0 | 68.0 |
| DATATYPE_MISMATCH | 60.5 | 9.0 |
| AMBIGUOUS_REFERENCE | 90.0 | 84.0 |
| SEMANTIC_ERROR | 93.0 | 31.0 |
| ALL | 86.3 | 63.4 |

Grammar and table errors are almost always restored exactly. DATATYPE_MISMATCH has low exact recovery by design:
the intended value behind `age > 'young'` cannot be inferred, and the engine only repairs when it can (`'5'`,
`'thirty'`, casts).

### 5.3 Text-to-SQL with verification

The same 150 Spider-dev questions are answered by two generators: a fine-tuned T5-small text-to-SQL model and
the instruction-tuned code LLM Qwen2.5-Coder-0.5B-Instruct (zero-shot, schema given as CREATE TABLE statements).
The pipeline verifies the first candidate, generates alternatives only if it is rejected, and repairs the best
candidate when none is valid.

| Generator | Pipeline | Valid SQL | Execution accuracy |
|---|---|---|---|
| Qwen2.5-Coder-0.5B-Instruct | raw top-1 | 54.0 | 40.0 |
| Qwen2.5-Coder-0.5B-Instruct | + verify & select | 74.0 | 49.3 |
| Qwen2.5-Coder-0.5B-Instruct | + repair | 88.0 | 54.7 |
| t5-small-awesome-text-to-sql | raw top-1 | 34.7 | 16.0 |
| t5-small-awesome-text-to-sql | + verify & select | 43.3 | 20.0 |
| t5-small-awesome-text-to-sql | + repair | 66.7 | 22.0 |

Verification and repair help both generators. Validity gains are larger than execution-accuracy gains, because a
valid query is not necessarily the intended one; the generator's understanding of the question is the limiting
factor, which is why the stronger generator benefits most in absolute terms.

## 6. Limitations

Errors are synthetic apart from the text-to-SQL study; the analyzer follows SQLite semantics plus portable rules;
the classifier is trained on analyzer labels and therefore approximates, rather than exceeds, the analyzer when a
schema is available. Its value is in the schema-free setting, in calibrated probabilities and in explanations.
Larger encoders (e.g. CodeBERT-base, see `notebooks/train_codebert_gpu.ipynb`) are expected to close part of the
UNKNOWN_COLUMN gap. NL2SQL with the code LLM takes tens of seconds per question on a laptop CPU; a GPU reduces
this to about a second.
